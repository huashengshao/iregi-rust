# Next emitter experiment: share column-operation kernels

This is a source-only proposal. No new implementation, compilation or numerical run is authorized by this document. The measured dense-loop candidate remains rejected.

The candidate did create a real multi-sample machine-code path. The retained B0 disassembly at 0x1a9878–0x1a98d2 performs packed arithmetic, stores two 16-byte complex outputs, advances 32 bytes and decrements the lane counter by two. This establishes that contiguous-loop emission can enable useful code generation; it does not establish a net runtime benefit. B0 homogeneous batches improve about 2.1%, but grouped batches regress. All three C0 batch orders regress.

The cost evidence is also concrete. C0 source grows 27.6%, while attributable named text grows 180.2%; B0 text grows 149.9%. C0 outlining changes from 81 to 92 blocks even though the mathematical/control graph is identical. Existing outlining cuts at 128 instructions or 32 KiB of source, so duplicated loop bodies change extraction boundaries. Each arithmetic instruction now branches between two emitted bodies, including on sparse and empty active sets. Static expansion, changed function boundaries and repeated dispatch are plausible causes of additional front-end, branch or instruction-cache cost. No hardware cache-miss or branch-miss counters were collected, so none is established as the sole cause. D0 allocator singleton differences likewise cannot establish allocator benefit because its scalar source is byte-identical.

The next candidate should emit one call per binary Add/Mul instruction into a small shared column kernel, while retaining the existing graph order and branch machinery. The shared kernel should call exactly the existing native `inline_add` or `inline_mul`, with unchanged operand order and constants. Dense versus sparse iteration belongs inside this shared kernel, once per numeric type and supported operand form, rather than duplicating arithmetic and loop machinery at every graph instruction. Prevent reinlining into thousands of call sites during the experiment. The existing `Outlines` registry can own and deduplicate these helper definitions; source-level keys must represent operation and operand form, while actual slot/constant identities remain explicit call arguments.

Start with binary operations, which account for 142 of 167 B0 Add/Mul instructions and 2,553 of 3,215 C0 Add/Mul instructions in the retained root/helper provenance. This is an operation-shape rule across all graphs, not a switch for a particular fixture, mass pattern or topology. Preserve all other instructions and higher arities initially. Never commute operands to combine constant/slot cases: native Float and DoubleFloat precision/rounding behavior can depend on the original expression order. Do not replace native primitives with Symbolica interpreter arithmetic merely because both implement the same mathematical operation; the existing cross-backend differences are explicitly recorded.

Reuse the existing disjoint-column borrowing pattern from native `copy_column`/`copy_active_column` to present bounded slices where possible. A target that aliases either source must use an explicit read-before-write path; equal sources must remain two operands of the original primitive. A shared constant remains a broadcast operand with its exact Context representation, not a reconstructed or precision-padded value. Dynamic dispatch, helper-call overhead and operand-category checks are risks to measure. A shared implementation reduces duplication opportunities but is not itself a proof of smaller machine code or faster execution.

The existing-facilities audit has three parts. First, the pinned Symbolica `BatchExpressionEvaluator` already shares Add/Mul execution code across instructions, retains a temporary to finish reads before overwriting a slot, and preserves lazy branches. Its evaluator/source is the model for instruction-major operation sharing; its arithmetic must not be substituted into the native path. Second, oneloopmaster's emitter tests already exercise outlined branch boundaries and aliased joins, and its native batch tests cover active-column copying with retained stride. Its primitives and `Outlines` registry provide the reusable arithmetic and factoring facilities. Third, searches through the supplied FeynKit/gammaloop tree and project usages found no directly reusable shared native Add/Mul column kernel or contiguous-active iterator abstraction. This is a bounded local API/source/use audit, not a claim about every upstream implementation. The proposed addition is storage/iteration plumbing around existing arithmetic, not a new algebra implementation.

If implementation is later authorized, preserve the same full ordered primitive/control/slot proof and six-output physical comparisons, including the nonzero-origin, sparse-hole, empty-reactivation, alias and invalid-neighbor fixture. Qualify f64, DoubleFloat and Float with precision/signed-zero checks before generic adoption, and verify the unchanged Dualizer route separately. Measure named text size, outline counts, compile scope, and the same homogeneous/mixed batch families. An isolated hardware-counter run, if permitted, should collect front-end/branch/cache evidence without becoming the primary timing gate. No repeated timing of the rejected candidate is proposed, and no speed claim is made for the alternative.
